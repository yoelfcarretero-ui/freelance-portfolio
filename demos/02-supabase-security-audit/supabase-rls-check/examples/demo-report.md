## Findings

### F-01 [Critical] Table "bookings" can be read by anyone on the internet

*Area:* Database / RLS &middot; *Check:* `DB-READABLE`

**What this means**

Using only the public key that ships inside your website, we were able to read rows from "bookings". This usually means Row Level Security (RLS) is turned off for this table, or a policy allows everyone to read it. Anyone can copy this key from the browser and download the whole table with a single request.

**Evidence**

- GET /rest/v1/bookings?select=*&limit=1 returned HTTP 200 with at least 1 row.
- Columns exposed: id, customer_name, customer_phone, starts_at, user_id
- Potentially sensitive columns: customer_phone
- Row values were not stored in this report.

**Business impact**

Data breach. Customer personal data can be scraped in bulk, which can trigger GDPR notification duties, fines and loss of trust. If write policies are also missing, the data may be modifiable too.

**Recommended fix**

Enable RLS and add explicit policies for each operation. Example for a table owned by a user:

```sql
alter table public.bookings enable row level security;

create policy "bookings: owner can read"
  on public.bookings for select
  to authenticated
  using ((select auth.uid()) = user_id);

create policy "bookings: owner can insert"
  on public.bookings for insert
  to authenticated
  with check ((select auth.uid()) = user_id);
```

Adjust `user_id` to your ownership column. If the data is genuinely public (e.g. a product catalogue), keep a `for select to anon` policy but make sure no private columns live in that table.

**References**

- https://supabase.com/docs/guides/database/postgres/row-level-security
- https://supabase.com/docs/guides/database/database-advisors?lint=0013_rls_disabled_in_public

### F-02 [Critical] Bucket "id-documents" is public

*Area:* Storage &middot; *Check:* `STORAGE-PUBLIC-BUCKET`

**What this means**

Files in the public bucket "id-documents" can be downloaded by anyone who has (or guesses) the file URL, with no login and no access rules applied. The bucket name suggests it holds private documents, which should never be public.

**Evidence**

- Bucket "id-documents" (id: id-documents) has public = true.
- Objects were not listed or downloaded by this tool.

**Business impact**

Exposure of identity documents or other personal files: a serious GDPR incident and a direct risk of identity fraud for your customers.

**Recommended fix**

Make the bucket private and serve files through short-lived signed URLs:

```sql
update storage.buckets set public = false where id = 'id-documents';

create policy "id-documents: users read own folder"
  on storage.objects for select to authenticated
  using (bucket_id = 'id-documents' and (storage.foldername(name))[1] = (select auth.uid())::text);
```

In the app: `supabase.storage.from('id-documents').createSignedUrl(path, 60)` instead of `getPublicUrl`.

**References**

- https://supabase.com/docs/guides/storage/security/access-control
- https://supabase.com/docs/guides/storage/buckets/fundamentals

### F-04 [Medium] 1 database function can be called from the browser

*Area:* RPC functions &middot; *Check:* `RPC-REVIEW`

**What this means**

These Postgres functions are exposed as API endpoints. Any visitor with the public key can call them unless execute permission was revoked. If a function is declared SECURITY DEFINER it runs with the privileges of its owner (often a superuser-like role) and skips Row Level Security entirely, so a single careless function can undo all your table policies. These were listed only, not executed.

**Evidence**

- rpc/get_bookings_for_day(day, salon_id)

**Business impact**

A SECURITY DEFINER function that reads or writes by an ID passed in from the client lets attackers read or change other users' data. Functions without a fixed search_path can also be hijacked by objects created in another schema.

**Recommended fix**

Review each function. List the risky ones with:

```sql
select p.proname, p.prosecdef as security_definer, p.proconfig as settings,
       has_function_privilege('anon', p.oid, 'execute') as anon_can_execute
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public';
```

Then, for each function:

```sql
-- Prefer SECURITY INVOKER so RLS applies (Postgres 15+ default for new functions).
alter function public.my_function(uuid) security invoker;

-- If it really must be SECURITY DEFINER, pin the search_path and check auth.uid() inside it.
alter function public.my_function(uuid) set search_path = '';

-- Remove access for roles that do not need it.
revoke execute on function public.my_function(uuid) from anon, public;
```

**References**

- https://supabase.com/docs/guides/database/functions#security-definer-vs-invoker
- https://supabase.com/docs/guides/database/database-advisors?lint=0011_function_search_path_mutable

### F-05 [Medium] Email confirmation is turned off

*Area:* Authentication &middot; *Check:* `AUTH-EMAIL-AUTOCONFIRM`

**What this means**

New accounts are active immediately without proving they own the email address. Someone can sign up as "ceo@yourcompany.com" or as one of your customers and the app will trust that address.

**Evidence**

- GET /auth/v1/settings: mailer_autoconfirm = true

**Business impact**

Fake and spam accounts, impersonation of real customers, and abuse of any feature that trusts the email (invitations, domain-based access, notifications).

**Recommended fix**

Dashboard: **Authentication > Sign In / Providers > Email > Confirm email** = on. Configure a custom SMTP provider so confirmation emails are delivered reliably.

**References**

- https://supabase.com/docs/guides/auth/auth-email

### F-06 [Low] Your full database schema is visible with the public key

*Area:* Database / RLS &middot; *Check:* `API-SCHEMA-PUBLIC`

**What this means**

Anyone holding the public (anon) key, which is shipped inside your website, can download a machine-readable list of every table, column and function exposed by the API. This is not a leak of data by itself, but it gives an attacker a free map of where to look.

**Evidence**

- GET /rest/v1/ returned HTTP 200 with 3 tables/views and 1 RPC functions.

**Business impact**

Makes reconnaissance trivial. Combined with a missing RLS policy, an attacker knows exactly which table to read.

**Recommended fix**

Keep internal tables out of the `public` schema (use a private schema that is not listed under *Exposed schemas* in API settings).
Newer Supabase projects can restrict OpenAPI access to the secret key; check **Project Settings > API**.
Most importantly, make sure every exposed table has RLS enabled (see the other findings).

**References**

- https://supabase.com/docs/guides/api/securing-your-api

### F-09 [Info] Anyone can create an account

*Area:* Authentication &middot; *Check:* `AUTH-SIGNUP-OPEN`

**What this means**

Public sign-up is enabled. That is normal for consumer apps, but for internal tools or invite-only products it means strangers can create accounts and reach whatever "authenticated" users can see.

**Evidence**

- GET /auth/v1/settings: disable_signup = false

**Business impact**

If your RLS policies only check "is logged in" (`to authenticated using (true)`), every stranger who signs up gets that access.

**Recommended fix**

If the app is invite-only, turn off **Allow new users to sign up**. Otherwise make sure policies check ownership (`auth.uid() = user_id`), not just being logged in, and keep the Auth rate limits and CAPTCHA enabled.

**References**

- https://supabase.com/docs/guides/auth/rate-limits
- https://supabase.com/docs/guides/auth/auth-captcha

## Limitations

This is an automated, outside-in, read-only check. It is a strong first signal, not a complete audit.

- Auth rate limits, CAPTCHA, password strength and leaked-password protection are not exposed by /auth/v1/settings and must be checked in the dashboard.
- Table checks are read-only (one SELECT of at most 1 row per table). Missing INSERT/UPDATE/DELETE policies are not tested, because doing so would require writing data. Review policies per operation in the SQL editor.
- Results reflect the anonymous role only. Data visible to any logged-in user (policies such as `to authenticated using (true)`) requires a test with a normal user session.
- An empty result cannot distinguish "RLS enabled" from "table currently empty".
